# Test Setup Contract: Domain to Organization Mapping  (area: GeneralTests)

> Generated by The Analyst (Phase 1.6). Read by the Engineer (implements setup), the
> Healer and the Refiner (consult instead of blind-scanning on setup failures).

## BLOCKER — this feature cannot be exercised in the OSS run

The feature is **cloud-only, end-to-end**. Before any setup question is asked, the Engineer
must know the section will **never render** on the OSS binary:

- UI gate: `showDomainOrgMappings = config.isCloud === "true" && isMetaOrg.value`
  (`web/src/components/settings/OrganizationSettings.vue:146`).
- `config.isCloud` is a **build-time** constant: `VITE_OPENOBSERVE_CLOUD` (default `"false"`)
  — `web/src/aws-exports.js:34-36`. No runtime env var or test fixture can flip it.
- Backend gate: `POST /{org_id}/settings` only persists `domain_org_mappings` under
  `#[cfg(feature = "cloud")]` AND `org_id == "_meta"` (`src/api/management/src/request/organization/settings.rs:157-207`).

**Consequence:** the spec cannot be a set of green UI tests in this OSS run. The Architect should
plan the spec as parked `test.fixme` (or a positive-probe → clean-SKIP, mirroring the existing
enterprise-gating pattern below). The remainder of this contract documents the *would-be*
preconditions for the cloud case, so the setup is recorded even though it is not executable here.

## Streams / data the spec must establish

**None.** This is a settings CRUD feature — it reads/writes `domain_org_mappings` on the meta org's
settings document. There is no stream/ingestion precondition.

- `<meta org settings>` — the "data" is the `domain_org_mappings` array on the `_meta` org,
  seeded by `GET /api/_meta/settings` → `store.organizationData.organizationSettings.domain_org_mappings`
  (`MainLayout.vue:1206`, default `[]` at `MainLayout.vue:1162`).
  - `[shared/read-only]` for the "empty state" case (no mappings → `…-empty`).
  - `[per-test]` for add/edit/delete cases (each test mutates the list; use unique domains).

## How to create it (copy these EXACT patterns — do NOT invent setup)

- **Auth/org:** the run reuses the framework session — `navigateToBase` uses
  `process.env.ZO_BASE_URL` + `process.env.ORGNAME` (see
  `tests/ui-testing/playwright-tests/utils/enhanced-baseFixtures.js:141-148`). No custom login is
  needed inside the spec. On cloud, the meta org is selected via
  `?org_identifier=_meta` (the existing pattern:
  `settingsFormValidationPage.navigateToDomainManagement()` navigates to
  `/web/settings/general?org_identifier=_meta`, `settingsFormValidationPage.js:330-343`).
- **Navigate to the section:** `/web/settings/organization?org_identifier=<org>` then wait for the
  host save button — copy `navigateToOrganizationSettings()` at
  `tests/ui-testing/pages/generalPages/settingsFormValidationPage.js:109-115`. The mappings section
  renders below the Log Details fields (only when the cloud+meta gate passes).
- **Set up / assert mappings via API (if the Architect wants API-level coverage for the cloud case):**
  - Read: `GET ${ZO_BASE_URL}/api/_meta/settings` → `data.domain_org_mappings` (see
    `web/src/services/organizations.ts:69-71` `get_organization_settings`).
  - Write: `POST ${ZO_BASE_URL}/api/_meta/settings` with body `{ domain_org_mappings: [{domain, org_id, base_role, user_group?}] }`
    (see `web/src/services/organizations.ts:72-74` `post_organization_settings`; backend shape in
    `src/common/src/meta/organization.rs` `DomainOrgMapping`). Target `org_id` must already exist;
    `base_role` ∈ `admin|editor|viewer|allowed_user`; optional `user_group` must already exist in the target org.

## Preconditions / toggles

- **Cloud build** (`config.isCloud === "true"`) — NOT satisfiable in this OSS run.
- **Meta org selected** — `selectedOrganization.identifier === zoConfig.meta_org` (`meta_org` is
  always `"_meta"` in `/config`, `status/mod.rs:562`). On OSS the first half of the AND is already
  false, so this never matters.
- No SQL-mode / quick-mode / streaming toggle involved — this feature is unrelated to query modes.

## Gotchas (so the Healer/Engineer don't rediscover them)

- **The section silently absent is the *expected* OSS behavior, not a bug.** A test that waits for
  `settings-domain-org-mappings-add-btn` will time out forever on OSS. Do not "fix" the test to wait
  longer — plan it as `fixme`/skip.
- **Selector suffix inheritance:** `OFormInput`/`OFormSelect` surface the control at `-field` and the
  error at `-error` (e.g. `settings-domain-org-mapping-domain-input-field` / `…-error`), NOT at the
  bare `data-test`. See the existing trace/span selectors at
  `settingsFormValidationPage.js:27-29`.
- **Role label vs value:** the dropdown stores `allowed_user` but displays "User"; the row badge
  (`badgeRole`) does the same remap. Assert on stored values (`admin|editor|viewer|allowed_user`),
  not the localized label.
- **Payload guard:** the host only POSTs `domain_org_mappings` when the section rendered — so an OSS
  save will NOT include (or wipe) the field at all.
- **Backend validation (cloud only):** mapping to a missing `org_id` → 400 "No org with org id …
  found"; missing group → 400 "custom group … not found in org …"; bad role → 400.
