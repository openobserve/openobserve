## The governing constraint — the click budget

**Every task in this file is subject to this rule, not only group G.** It is not a nice-to-have to
be traded away when a screen gets busy; it is the acceptance criterion.

| Kind of thing | Budget |
|---|---|
| Reading an answer the product already knows — who is on call, would this page land, what broke last time | **0 clicks.** It is on the screen you already opened. |
| The primary action of a screen — acknowledge, resolve, take a cover, add a rule | **1 click** from the list the user is already looking at. |
| Any complete flow, start to saved | **2 clicks, 3 at the absolute limit.** |

Three rules that follow from it, and that a reviewer should reject a PR over:

1. **A navigation step is a click.** Rail → flyout → page → tab → button is four before the user has
   done anything. Deep-linking a tab does not make the tab free — it makes it shareable.
2. **Act from the row.** If a list can show a thing, it can act on it. The Pages triage list already
   gets this right — [OnCallResponses.vue:422](src/views/OnCall/OnCallResponses.vue#L422) acknowledges
   and resolves inline and offers a bulk action, so acking a page is **1 click**. Every other on-call
   list should be held to that standard.
3. **Pre-fill from context.** A form opened from a gap, a shift or a failing rule must arrive with
   the window, the person and the reason already filled. The click you remove is the one where the
   user re-types what the app already knew.

**What this costs, stated honestly:** a 2-click ceiling is not reachable for genuinely multi-part
setup — building a follow-the-sun schedule from scratch is not a two-click act. That is exactly why
**C8/C9 (presets)** and **F3 (preview before save)** matter: a preset turns a ten-field construction
into *pick a shape → confirm*. Where a flow cannot fit the budget, the fix is a better default, not a
shorter form.

## F. incident.io-informed UX

Researched against incident.io's live on-call documentation (sources at the bottom). Their setup path
is **Teams → Schedules → Escalation paths → Alert sources → Alert routes** — five named screens in a
fixed order, each one a prerequisite for the next.

builder does not offer.

escalation path on priority and working hours; we key a separate ladder per priority (P1–P5) and
express working hours as restriction windows on the rotation. Same outcomes, different shape — do not
